# 3단계 재검증과 4단계 진행 판단

2026-10-11 현재 코드, 기존 전체 산출물, 대표 영상 재실행, 독립 합성 입력을 검사했다. **4단계 기능 개발은 진행할 수 있지만, 3단계 속도 정확도가 완성됐다고 판단할 수는 없다.** 구현 동작과 실제 측정 정확도를 구분해야 한다.

이후 사용자가 테스트 1~4의 슬로모션, 테스트 12~14의 카메라 설정 차이 의심, 실촬영 10~13의 줌아웃 조건을 설명했다. [촬영 조건과 검증 대상](ai_capture_conditions.md)에 파일 FPS·해상도와 함께 반영했다. 조건 미확인 영상에 같은 보정·시간 기준을 적용한 기존 결과를 실제 속도의 기준으로 삼지 않는다.

## 확인한 근거

| 검사 | 결과 | 의미 |
|---|---|---|
| Python 단위·SSE 라우트 검사 | 37개 통과 | 좌표 변환, 이상 보정, 구간 선택, 모델 계산, 반환 필드 동작 |
| 기존 전체 32개 산출물 | 해시·3D 출처·시간·이미지·MP4 검사 통과 | 현재 분석 모듈·모델·입력과 기존 실행이 일치 |
| 대표 영상 3개 새 실행 | 실촬영 4번 95.2km/h / 실촬영 14번 모델 불일치로 보류 / 테스트 8번 이동으로 보류 | 서로 다른 결과 분기가 이전과 동일하게 재현됨 |

전체 32개를 다시 AI 추론한 것은 아니다. 기존 32개는 파일 해시와 산출물을 재검사했고, 대표 3개만 모델 추론부터 새로 실행했다. 원본 전체 실행 결과는 여전히 추정 15개, 계산 보류 17개다. 합성 보정 파일은 검사 출력 폴더에만 저장했고 실제 서비스 보정으로 등록하지 않았다.

## ‘완벽’으로 판단할 수 없는 이유

모델 검사는 검출한 위치·공 크기와 계산의 일관성을 평가한다. **잘못된 카메라 가정이나 공 크기가 일관되게 사용되면, 선이 잘 맞아도 속도는 틀릴 수 있다.** 독립적으로 알려진 탄도와 구 투영을 만든 입력에서 다음을 확인했다.

| 합성 조건 | 정답 구간 평균 속도 | 반환값 | 판정 |
|---|---:|---:|---|
| 정확한 내부 행렬·공 크기 | 73.15km/h | 73.2km/h | ESTIMATED |
| 실제 화각 90°에 기본 가정 60° 적용 | 73.15km/h | 125.3km/h | ESTIMATED, 약 71% 오차 |
| 정확한 내부 행렬, 공 박스가 항상 20% 큼 | 73.15km/h | 55.6km/h | ESTIMATED, 약 24% 오차 |

위 수치는 합성 사례에서의 오차이며 기존 32개 영상의 실제 오차율을 뜻하지 않는다. 작은 투영 오차나 `ESTIMATED`를 속도 정확도의 증거로 사용할 수 없다는 점을 보여준다.

현재 남은 조건은 다음과 같다.

- **실제 내부 보정·촬영 자세·정답 속도:** 32개 모두 실제 보정 없이 화각을 가정했다. 중력도 카메라 아래 방향을 가정한다. 같은 카메라의 렌즈·줌·크롭 조건과 독립 기준 속도가 필요하다.
- **공 크기의 체계적 오차:** YOLO 박스가 흐림·부분 가림 때문에 일정하게 커지거나 작아지면 속도 보류 검사로 모두 잡을 수 없다. 실제 공 중심·윤곽을 대조해야 한다.
- **시간 기준:** FPS가 없으면 분석기가 30FPS를 가정하며, 속도 계산이 `fps_fallback`을 이유로 보류하지 않는다. 현재 검증 영상에는 FPS fallback이 없지만 이 입력 조건의 방어는 보완 대상이다. 슬로모션 재생 FPS와 실제 촬영 FPS도 구분해야 한다.
- **카메라별 보정 선택:** 하나의 보정 파일을 전역으로 사용한다. 다른 카메라 영상인지 자동 확인하지 않는다. 같은 촬영 장비·설정인지 사용자가 관리해야 한다.
- **측정 구간과 골대 평면:** 3D 모델은 최대 0.45초의 초기 비행만 다룬다. 골대 사각형도 영상의 검출 영역이다. 경기장 좌표·골대 평면·전 구간 충돌을 복원하지 않았다.

## 이번 검토에서 수정한 부분

AI 계산 알고리즘과 모델 가중치는 변경하지 않았다. 계산 결과 비교를 유지하면서 아래의 화면·검사·문서를 보완했다.

- 업로드 화면의 구현되지 않은 ‘스마트폰 렌즈 자동 추출’ 안내를 실제 체커보드 보정 안내로 수정했다.
- 보정 화면이 네트워크 청크마다 JSON을 바로 읽던 문제를 수정했다. 이벤트가 여러 청크로 나뉘어도 모아서 읽고 결과 없이 연결이 끝나면 오류를 표시한다.
- 체커보드 안내를 내부 교차점 9×6개, 실제 칸 수 10×7로 명확히 했다.
- 전체 산출물 검사에 보정 파일 존재 여부·해시 검사도 추가했다.
- README의 2단계 설명을 현재 3단계 계산·화면·검증 상태로 갱신했다.

## 4단계에서 사용할 범위

**골대 진입 후보, 판정 보류, 결과 표시와 점수 규칙 구조 개발은 시작해도 된다.** 공의 전체 비행 관측은 `trajectory`를 사용하고, 초기 구간의 `fitted_trajectory`를 골대까지 연장해 판정하지 않는다. 속도 `null`, 골대·공 가림, 관측 부족을 정상적인 ‘판정 불가’ 상태로 처리해야 한다.

골인 확정에는 공 전체의 골대 평면 통과를 뒷받침하는 촬영·기하 근거가 필요하다. 영상에서 공 중심이 골대 사각형에 들어온 사실만으로 확정하지 않는다. 현재 추정 속도를 정확한 측정값으로 취급하는 점수 계산도 보류한다.

4단계 기능 개발과 함께 실촬영의 계산 보류 6개에서 중심·공 크기를 확인하고, 실제 보정·기준 속도로 측정 검증을 진행하는 순서를 권장한다. FPS 미확인 처리와 카메라별 보정 선택도 측정 기능의 완료 전에 보완한다. 이번 요청에서는 4단계 구현을 시작하지 않았다.
