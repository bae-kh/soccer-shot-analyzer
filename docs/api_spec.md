# API Specification

Base URL (개발 환경): http://localhost:8000

CORS: 모든 origin/method/header 허용 (backend/main.py CORSMiddleware 설정 기준)

공통 사항:

- 진행률/결과를 실시간으로 전달하는 엔드포인트(/analyses/{analysis_id}/events)는 Content-Type: text/event-stream인 SSE(Server-Sent Events)로 응답한다. 보정은 SSE 대신 폴링을 쓴다.
- SSE 응답은 한 줄씩 data: {JSON} 형식(줄 끝에 빈 줄 포함)으로 전송되며, 클라이언트는 type 필드로 이벤트 종류를 구분한다.

---

## 1. 영상 분석 (job 기반 분리 설계)

3주차에 확정한 설계로, 업로드/분석 실행과 진행률 구독을 분석 id 기준으로 분리한다. 분석이 오래 걸리는 동안 연결이 끊겨도(새로고침, 탭 재접속) 분석 id로 다시 붙어 상태를 확인할 수 있도록 하는 것이 목적이다.

3주차에 설계하고 간트차트상 10주차 구현으로 두었으나, 프론트엔드가 5주차에 이 구조를 전제로 API 계층을 구현하면서 일정을 앞당겼다. 프론트엔드가 브라우저 표준 EventSource로 진행률을 구독하는데 EventSource는 GET 요청만 보낼 수 있어, 업로드와 구독이 한 요청에 묶여 있으면 연결 자체가 불가능하기 때문이다. 6주차에 구현을 완료했다.

경로와 이벤트 명칭은 프론트엔드가 이미 작성한 코드 기준으로 맞췄다. 백엔드 명세는 문서라서 수정 비용이 더 낮다고 판단했다.

### 1.1 POST /analyses

영상을 업로드하고 분석 job을 생성한다. SSE를 열지 않고 즉시 분석 id를 반환한다.

#### Request

| 항목         | 값                                      |
| ------------ | --------------------------------------- |
| Method       | POST                                    |
| Content-Type | multipart/form-data                     |
| Body         | file 필드: 축구 슈팅 영상 파일 (mp4 등) |

#### Response

| 상태 코드 | Body                          |
| --------- | ----------------------------- |
| 202       | { "id": "문자열(uuid4)" } |

업로드 유효성 검증(아래 표)에 걸리면 202 대신 400/413/415를 즉시 반환한다.

### 1.2 GET /analyses/{analysis_id}/events

해당 job의 진행률과 결과를 SSE로 구독한다.

#### Request

| 항목           | 값                                |
| -------------- | --------------------------------- |
| Method         | GET                               |
| Path Parameter | analysis_id: POST /analyses 응답의 id 값 |

#### Response

Content-Type: text/event-stream (분석 id가 존재하는 경우)

이벤트 종류는 progress, keepalive, complete, failed 네 가지다 (아래 SSE 이벤트 표, Result 객체 참고).

동작 규칙:

- job이 실행 중일 때 연결하면, 그 시점 이후의 progress 이벤트를 실시간으로 받다가 완료되면 complete 이벤트를 받고 스트림이 닫힌다.
- job이 이미 완료된 뒤에 연결하면(재접속 시나리오), 지난 progress는 재생하지 않고 complete 이벤트만 즉시 받은 뒤 스트림이 닫힌다.
- 분석 id가 존재하지 않으면 SSE 대신 404 JSON(error_code: JOB_NOT_FOUND)을 반환한다.

### 1.3 GET /analyses/{analysis_id}/result

SSE 연결 없이 현재 상태만 확인하는 폴링용 엔드포인트. 분석 작업 상태 조회 요구를 이 엔드포인트로 해결한다.

#### Response

| 상태 코드 | Body                                                      |
| --------- | --------------------------------------------------------- |
| 200       | Result 객체 (분석이 끝난 경우)                            |
| 202       | { "status": "RUNNING", "progress": 0~100 } (아직 진행 중) |
| 404       | { "error_code": "JOB_NOT_FOUND" }                         |
| 500       | { "error_code": "ANALYSIS_ERROR" } (분석 중 서버 예외)    |

### 1.4 GET /analyses/{analysis_id}/video

분석에 사용한 원본 영상을 반환한다. 프론트엔드가 이 영상 위에 SVG로 궤적을 그리기 때문에 필요하다.

#### Request

| 항목           | 값                                |
| -------------- | --------------------------------- |
| Method         | GET                               |
| Path Parameter | analysis_id: POST /analyses 응답의 id 값 |

#### Response

| 상태 코드 | Content-Type                    | Body                       |
| --------- | ------------------------------- | -------------------------- |
| 200       | video/mp4 또는 video/quicktime  | 원본 영상 바이너리         |
| 404       | application/json                | error_code: JOB_NOT_FOUND 또는 VIDEO_NOT_FOUND |

주의할 점:

- 브라우저 video 태그의 탐색(seek)에 필요한 Range 요청을 지원한다. 사용 중인 웹 프레임워크의 파일 응답이 accept-ranges 헤더를 붙이고 206 부분 응답을 처리하므로 별도 구현은 하지 않았다 (7주차 확인 완료).
- 파일 보관 정책에서 정한 보관 기간이 곧 "결과를 다시 볼 수 있는 기간"이 된다. 영상이 정리된 뒤에는 분석 id가 살아 있어도 VIDEO_NOT_FOUND가 된다.
- 분석 작업 정보에 원본 영상 경로를 함께 보관하여 어느 파일인지 찾는다. 작업 정보가 서버 메모리에 있으므로 서버를 재시작하면 파일이 남아 있어도 조회할 수 없다.

### 궤적 시각화 방식 (4주차 결정)

궤적은 프론트엔드가 SVG로 그린다. 백엔드는 좌표 배열(Result의 trajectory)과 원본 영상만 제공하고, 화면에 그리는 일은 프론트엔드가 담당한다.

- trajectory 좌표는 { "x": 숫자, "y": 숫자 } 객체의 배열이며, **원본 영상 해상도 기준 픽셀 좌표**로 반환한다. 프론트엔드가 SVG viewBox를 영상 원본 좌표계와 동일하게 설정하는 방식과 맞춘 규격이다.
- 좌표 기준 해상도는 frame_size 필드로 내려준다. 백엔드는 영상을 축소하지 않고 원본 해상도로 분석하므로 프론트엔드가 읽는 실제 영상 해상도와 같은 값이지만, 프론트엔드가 환산 계수를 계산하는 기준으로 쓰기 위해 명시한다.
- 각 궤적 점에는 0부터 시작하는 프레임 번호(frame)가 붙는다. 영상의 초당 프레임 수(fps)와 함께 쓰면 재생 시간과 궤적 위치를 맞출 수 있다. 프론트엔드가 궤적 점을 눌러 해당 시점으로 영상을 이동시키는 기능에 쓰인다.
- 분석 코드는 calibration.json이 있으면 왜곡 보정(undistort)된 프레임에서 좌표를 추출한다. 반면 이 API가 돌려주는 영상은 보정 전 원본이므로, 보정 좌표를 그대로 쓰면 궤적이 어긋난다. 따라서 trajectory는 보정 좌표를 다시 왜곡시켜 **원본 영상 좌표계 기준**으로 되돌린 값을 반환한다 (5주차 구현 완료).
- 이 변환은 출력용 trajectory에만 적용한다. 궤적 피팅은 왜곡 없는 핀홀 카메라 모델을 전제로 하므로, 피팅 입력에는 보정된 좌표를 그대로 사용한다.

기존의 결과 오버레이 이미지(trajectory_image, GET /results)를 계속 유지할지는 아직 정하지 않았다. 백엔드가 이미지를 그리는 작업과 프론트엔드가 SVG로 그리는 작업이 중복되기 때문이다. 다만 README와 시연 자료가 현재 오버레이 이미지를 사용하고 있어, 당장 제거하지 않고 유지 여부를 팀에서 확인한다.

### 아직 정하지 못한 부분

- job 저장소는 서버 메모리(딕셔너리)로 두기로 했다. 서버를 재시작하면 진행 중이던 job이 모두 사라지지만, MVP 단계에서 데이터베이스를 도입할 필요는 없다고 판단했다.
- 분석 취소(DELETE /analyses/{analysis_id}): CV 처리 루프 자체를 중간에 끊는 것이 어려워, "취소 요청은 받되 이미 시작된 분석은 끝까지 실행하고 결과만 폐기"하는 정도가 현실적인 선으로 보고 있다. 최종 확정은 10주차 구현 시점에 한다.
- 완료된 job을 메모리에서 언제 정리할지 (파일 보관 정책과 같은 종류의 문제)

### 업로드 파일 유효성 검증

job을 생성하기 전에 아래 조건을 검사하고, 위반 시 202 대신 일반 JSON 오류 응답을 즉시 반환한다.

| 상태 코드 | 조건                           | 응답 예시                                                                               |
| --------- | ------------------------------ | --------------------------------------------------------------------------------------- |
| 400       | file 필드 누락 등 잘못된 요청  | { "error_code": "MISSING_FILE", "message": "영상 파일이 필요합니다" }                   |
| 413       | 업로드 용량 초과 (200MB)       | { "error_code": "FILE_TOO_LARGE", "message": "업로드 가능한 최대 용량을 초과했습니다" } |
| 413       | 영상 길이 초과 (30초)          | { "error_code": "VIDEO_TOO_LONG", "message": "업로드 가능한 최대 길이를 초과했습니다" } |
| 413       | 영상 길이 미달 (1초)           | { "error_code": "VIDEO_TOO_SHORT", "message": "영상이 너무 짧습니다" }                  |
| 415       | 허용되지 않은 확장자/MIME 타입 | { "error_code": "UNSUPPORTED_MEDIA_TYPE", "message": "지원하지 않는 형식의 파일입니다" } |
| 415       | 해상도 미달 (짧은 변 480px)    | { "error_code": "RESOLUTION_TOO_LOW", "message": "영상 해상도가 너무 낮습니다" }        |
| 415       | 영상 정보를 읽을 수 없음       | { "error_code": "UNREADABLE_VIDEO", "message": "영상을 읽을 수 없습니다" }              |

**검증 기준값 (6주차 확정)**

| 항목          | 기준                        |
| ------------- | --------------------------- |
| 허용 확장자   | mp4, mov (video/mp4, video/quicktime) |
| 최대 용량     | 200MB                       |
| 영상 길이     | 1초 이상 30초 이하          |
| 최소 해상도   | 짧은 변 480px 이상          |

허용 확장자는 스마트폰 기본 카메라 앱이 생성하는 가장 일반적인 컨테이너 포맷을 기준으로 정했다. 나머지 세 기준은 프론트엔드가 5주차에 적용하고 경계값 단위 테스트까지 수행한 값을 그대로 채택하여, 화면과 서버의 판정 결과가 어긋나지 않도록 하였다. 해상도는 스마트폰 세로 영상을 고려하여 긴 변이 아닌 짧은 변을 기준으로 판단한다.

**검증 순서와 처리 방식**

1. 파일 누락과 확장자는 저장 전에 검사한다.
2. 용량은 파일을 저장하는 동안 누적 크기를 확인하여, 한도를 넘는 순간 저장을 중단하고 쓰다 만 파일을 삭제한다. 한도 초과 파일을 끝까지 기록하지 않기 위한 처리이다.
3. 길이와 해상도는 영상 메타데이터를 읽어야 하므로 저장 후에 검사하며, 조건에 걸리면 저장된 파일을 삭제한 뒤 오류를 반환한다.

보정 요청(POST /calibrations)도 같은 검증을 쓰되 최소 길이만 5초로 다르다.

### SSE 이벤트 종류 (GET /analyses/{analysis_id}/events 응답)

| type      | 설명                                         | 예시 payload                                |
| --------- | -------------------------------------------- | ------------------------------------------- |
| progress  | 분석 진행률 (0~100). 값이 바뀔 때만 전송     | type: progress, value: 45                     |
| keepalive | 진행률 갱신이 없는 동안 연결 유지용으로 전송 | type: keepalive                               |
| complete  | 분석 완료 결과                               | type: complete, data: (아래 Result 객체 참고) |
| failed    | 분석 수행 자체가 불가능한 서버 예외          | type: failed, message: 에러 메시지            |

complete와 failed의 구분 기준은 2주차에 정한 원칙 그대로다. 분석 파이프라인이 끝까지 실행되면 신뢰도 미달이든 공 미탐지든 complete로 보내고 Result의 status로 구분한다. 모델 로드 실패처럼 분석 자체를 수행하지 못한 경우만 failed로 보낸다.

### Result 객체

2주차 발표자료 수정본에서 확정한 스키마 기준이다. 기존 api_spec.md 초안에 있던 score, speed, trajectory_image는 유지하고, status, goal, trajectory, confidence, processing_time_sec, failure_reason을 추가했다.

| 필드                | 타입   | 설명                                                                                           |
| ------------------- | ------ | ---------------------------------------------------------------------------------------------- |
| status              | enum   | VALID 또는 ANALYSIS_FAILED                                                                     |
| score               | int    | 슈팅 점수 (0~100, 속도 기반 산정: min(100, speed_kmh 나누기 1.3))                              |
| speed_kmh           | float  | 추정 슈팅 속도 (km/h, 최대 150으로 상한)                                                       |
| goal                | bool   | 골인 여부 판정 (로직 미구현, 현재는 항상 false 반환 예정)                                      |
| trajectory          | array  | 공 궤적 좌표 시퀀스. { "x": 숫자, "y": 숫자, "frame": 정수 } 객체의 배열이며 원본 영상 해상도 기준 픽셀 좌표. frame은 0부터 시작하는 프레임 번호 |
| fps                 | float  | 영상의 초당 프레임 수. 프론트엔드가 재생 시간과 궤적을 맞추는 데 사용 |
| frame_size          | object | 좌표 기준 해상도. { "width": 정수, "height": 정수 } |
| confidence          | float  | 분석 신뢰도 (0~1)                                                                              |
| processing_time_sec | float  | 분석 소요 시간 (초). 측정 구간은 업로드 파일 저장 완료 시점부터 결과 생성 완료 시점까지로 한다 |
| failure_reason      | string | 실패 시 원인 코드 (status가 ANALYSIS_FAILED일 때만 포함, 아래 표 참고)                         |
| trajectory_image    | string | 결과 오버레이 이미지 파일명 (GET /results/이미지이름 으로 조회)                                |

comment(코멘트 생성) 필드는 수정본 pptx에서 빠졌다. 신청서 9주차 과제가 "점수 및 코멘트 생성"으로 묶여 있으니, comment를 Result에 유지할지 별도로 다룰지는 아직 결정 필요 항목으로 남겨둔다.

### failure_reason 코드 목록

| 코드              | 의미                                 |
| ----------------- | ------------------------------------ |
| BALL_NOT_DETECTED | 정지 상태의 공을 찾지 못함           |
| TRACK_TOO_SHORT   | 추적된 궤적 포인트가 5개 미만        |
| FIT_FAILED        | 궤적 피팅(최적화) 실패               |
| GOAL_NOT_DETECTED | 골대를 인식하지 못해 scale 추정 불가 |
| LOW_CONFIDENCE    | confidence가 임계값 미만             |

프론트엔드는 분석 실패를 BALL_NOT_DETECTED, GOAL_NOT_DETECTED, INVALID_VIDEO 세 가지 화면으로 처리한다. 백엔드가 반환하는 코드와의 대응은 다음과 같다.

| 백엔드 failure_reason | 프론트엔드 화면        |
| --------------------- | ---------------------- |
| BALL_NOT_DETECTED     | BALL_NOT_DETECTED      |
| TRACK_TOO_SHORT       | BALL_NOT_DETECTED      |
| FIT_FAILED            | BALL_NOT_DETECTED      |
| LOW_CONFIDENCE        | BALL_NOT_DETECTED      |
| GOAL_NOT_DETECTED     | GOAL_NOT_DETECTED      |

뒤의 세 코드는 사용자 입장에서 모두 "공을 제대로 추적하지 못했다"에 해당하므로 같은 화면을 쓴다. 그럼에도 백엔드가 코드를 나눠 두는 이유는, 데이터 파트가 탐지 실패 사례를 분류해 데이터를 보완할 때 어느 단계에서 실패했는지를 구분해야 하기 때문이다. INVALID_VIDEO는 업로드 검증 단계의 413·415 응답을 프론트엔드가 변환한 것이라 failure_reason에는 나타나지 않는다.

confidence는 추적된 전체 프레임 중 객체 탐지에 성공한 프레임의 비율로 산출한다. 나머지 프레임은 추적기 보간으로 채워진 구간이므로, 이 비율이 낮을수록 궤적이 실제 관측보다 추정에 의존한다는 뜻이다. 후보였던 궤적 피팅 잔차 방식 대신 이 방식을 택한 이유는, 추적 로직이 이미 탐지 성공과 보간을 구분하고 있어 추가 연산이 필요 없고 값의 의미가 직관적이기 때문이다.

LOW_CONFIDENCE 임계값은 0.6이다. 추적 로직이 탐지 실패 시 최대 15프레임까지 보간으로 이어가는데 30fps 기준 0.5초에 해당하여, 궤적의 절반 이상이 보간 구간이면 속도 추정의 근거가 부족하다고 보았다. 실제 측정 데이터 없이 정한 잠정값이므로 평가용 영상의 탐지율 분포를 확인한 뒤 조정한다. 값은 backend/analyze_shot.py의 CONFIDENCE_THRESHOLD에서 변경한다.

status가 ANALYSIS_FAILED인 경우에도 동일한 Result 스키마로 응답한다. score와 speed_kmh는 0이며, trajectory는 추적이 시작되기 전에 실패한 경우(BALL_NOT_FOUND) 빈 배열이고 그 이후 단계에서 실패한 경우에는 그때까지 추적된 좌표가 담긴다.

### 진행률 구간 (참고)

- 0~15%: 정지 공 탐색 (Phase 1)
- 15~90%: 프레임별 탐지/추적 (Phase 2)
- 100%: 궤적 피팅 및 시각화 완료 (Phase 3)

## 3. 카메라 보정 (7주차 구현)

체스보드 영상으로 카메라 내부 파라미터와 왜곡 계수를 구한다. 프론트엔드가 7주차에 보정 화면을 구현하며 제안한 구조를 따랐다.

분석과 달리 **SSE를 쓰지 않고 폴링**한다. 분석은 정지 공 탐색·추적·궤적 피팅으로 단계가 나뉘어 진행률에 의미가 있지만, 보정은 단계 구분이 없고 처리 시간도 짧아 상태만 주기적으로 확인하면 충분하다는 프론트엔드 판단을 반영했다.

### 3.1 POST /calibrations

보정 영상을 업로드하고 보정 작업을 생성한다.

| 항목         | 값                                                 |
| ------------ | -------------------------------------------------- |
| Method       | POST                                               |
| Content-Type | multipart/form-data                                |
| Body         | file 필드: 체스보드가 촬영된 영상                   |

| 상태 코드 | Body                          |
| --------- | ----------------------------- |
| 202       | { "id": "문자열(uuid4)" }     |

업로드 검증은 분석과 같은 규칙을 쓰되 **최소 길이만 5초**로 다르다. 보정에는 여러 위치와 각도의 프레임이 필요하기 때문이다. 체스보드 규격은 내부 코너 9x6, 한 칸 25mm를 전제한다. 프론트엔드 안내 화면이 같은 값으로 인쇄용 파일을 만들므로 한쪽만 바꾸면 안 된다.

### 3.2 GET /calibrations/{calibration_id}

보정 작업의 상태와 결과를 조회한다. 프론트엔드는 1초 간격으로 호출한다.

| 상태 코드 | 조건      | Body                                                |
| --------- | --------- | --------------------------------------------------- |
| 202       | 진행 중   | { "status": "CALIBRATING", "progress": 0~100 }      |
| 200       | 성공      | 아래 성공 응답 참고                                  |
| 200       | 보정 실패 | { "status": "FAILED", "failure_reason": 코드, "used_frames": 정수 } |
| 404       | 없는 id   | { "error_code": "CALIBRATION_NOT_FOUND" }           |

성공 응답:

| 필드               | 타입   | 설명                                   |
| ------------------ | ------ | -------------------------------------- |
| status             | enum   | VALID                                  |
| frame_size         | object | 보정에 사용한 해상도 { width, height } |
| used_frames        | int    | 체스보드를 찾아 계산에 사용한 프레임 수 |
| reprojection_error | float  | 재투영 오차(px)                        |
| focal_length       | object | { fx, fy }                             |
| principal_point    | object | { cx, cy }                             |

재투영 오차의 품질 구분(0.5px 미만 양호, 1px 미만 보통, 그 이상 재촬영 권장)은 프론트엔드 화면 안내용 잠정 기준이며 백엔드는 값만 전달한다.

### 보정 실패 코드

| 코드                | 의미                                      |
| ------------------- | ----------------------------------------- |
| CHESSBOARD_NOT_FOUND | 어느 프레임에서도 체스보드를 찾지 못함    |
| NOT_ENOUGH_FRAMES   | 체스보드를 찾았으나 계산에 필요한 5장 미만 |
| VIDEO_OPEN_FAILED   | 영상을 열 수 없음                         |
| CALIBRATION_FAILED  | 보정 계산 자체가 실패                     |
| SAVE_FAILED         | 보정값 저장 실패                          |

체스보드를 아예 못 찾은 경우와 몇 장만 찾은 경우를 나눈 것은 사용자에게 줄 안내가 다르기 때문이다. 전자는 체스보드가 화면에 제대로 들어오지 않은 것이고, 후자는 더 많은 각도로 더 길게 찍어야 한다는 뜻이다.

### 아직 연결되지 않은 부분

보정 결과를 id별로 저장하지만, **분석 요청이 특정 보정을 골라 쓰는 연결은 아직 없다.** 프론트엔드는 보정 결과를 브라우저에 저장했다가 분석 요청에 calibration_id를 함께 보내도록 구현했으나, 백엔드 분석 코드는 여전히 고정된 파일 하나에서 보정값을 읽는다.

이를 연결하려면 분석 코드의 보정값 읽는 부분이 파일을 직접 열지 않고 값을 인자로 받도록 바뀌어야 한다. 해당 파일은 AI 파트가 작업 중이므로 협의 후 진행한다.

기존 POST /calibrate(SSE 방식)는 이 구조로 대체되어 제거했다.

## 파일 저장 및 보관 정책 (5주차 확정, 구현 완료)

업로드 영상과 결과 오버레이 이미지는 서버 로컬 디렉토리(backend/uploads)에 저장한다.

- 파일명 규칙: 업로드 시각과 원본 파일명을 조합한 이름으로 저장한다 (예: 20260929_030204_shot.mp4). 같은 이름의 영상을 다시 올려도 이전 결과가 덮어써지지 않는다. 파일명에서 경로 부분은 제거하여 업로드 폴더 밖에 파일이 생성되지 않도록 한다.
- 보관 기간: 7일. 마지막 수정 시각 기준으로 7일이 지난 파일은 정리한다.
- 정리 방식: 별도 배치 작업을 두지 않고, 새 업로드가 들어올 때마다 만료된 파일을 함께 정리한다. 요청이 없으면 정리도 일어나지 않지만, 요청이 없는 동안에는 저장 용량이 늘지도 않으므로 MVP 단계에서는 충분하다고 판단하였다.

보관 기간은 곧 결과를 다시 조회할 수 있는 기간이다. 7일이 지나면 분석 id가 살아 있어도 결과 이미지와 원본 영상을 받을 수 없다.

실제 저장 용량 사용 추이를 본 뒤 기간 조정이 필요하면 backend/main.py의 RETENTION_DAYS 값을 변경한다.

## 동시 분석 요청 처리 (3주차 조사)

현재 설계상 analyze 요청마다 별도 백그라운드 스레드에서 독립적으로 분석이 실행되는 구조라, 여러 사용자가 동시에 요청해도 요청 자체가 거부되지는 않는다.

위 1장의 job 기반 설계로 개별 job의 상태 조회(GET /analyses/{analysis_id}/result)와 취소 방향은 정했지만, 아래는 여전히 없다.

- 동시 실행 가능한 작업 수 제한 (자원 사용량 관리 없음)
- 전체 실행 중인 job 목록을 한눈에 보는 방법 (개별 분석 id로 조회하는 것과는 별개)

MVP 단계에서는 동시 요청 수가 적을 것으로 보고 별도 제한을 두지 않는 방향으로 우선 진행하고, 필요성이 확인되면 작업 큐 도입을 검토한다.
