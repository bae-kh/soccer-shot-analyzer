# 촬영 조건 연결의 합성 검증

2026-10-11. 사용자가 실제 촬영 정보·체커보드 자료는 아직 없다고 확인하여, 정답을 알고 있는 합성 영상과 관측값으로 보정·시간 환산·속도 계산을 검증했다. **실제 영상의 정답 속도를 검증한 결과가 아니다.** 이번 작업에서는 README를 수정하지 않았다.

## 실행한 검증과 수정

1. 초점거리가 다른 카메라 두 개의 체커보드 영상(각 24프레임)을 만들었다. 보정 SSE 라우트의 실제 OpenCV 계산 → 프로필 JSON 저장 → 프로필 목록 → 해당 카메라 설정 선택을 실행했다. 계산 함수를 모의 처리하지 않았다. 서버를 외부에 열지 않고 라우트 함수를 호출했다.
2. 독립적인 구의 투영식으로 정답 위치·공 크기를 만들어 선택한 보정과 실제 시간으로 속도를 계산했다. 정상 30/60FPS, 광각, 동일 비율 축소, 4배 슬로모션, 촬영 240FPS, 카메라를 향하는 공을 검사했다. 이 관측값은 YOLO 검출 결과가 아니므로 검출기 정확도 시험에 해당하지 않는다.
3. 시간이 미확인, FPS만 있고 프레임 저장 방식 미확인, 보정 누락·미등록, 카메라 설정 미확인, 크롭 여부 미확인, 다른 화면 비율, 카메라 이동의 8개 조건에서 속도가 null로 보류되는지 확인했다.
4. 30FPS에서 0.45초를 프레임 수로 반올림하면 14프레임 = 약 0.467초까지 선택되는 경계 오류를 찾았다. `backend/shot_physics.py`의 구간 끝을 내림하도록 수정하여 0.45초를 넘는 프레임을 제외했다. 30·59.94·120FPS의 회귀 테스트를 추가했다.

합성 자료·보정·업로드 파일은 `output/ai_baseline/stage3_capture_pipeline_20261011_recheck` 아래에만 저장했다. 실제 서비스의 촬영 조건 JSON·전역 보정·보정 프로필을 변경하지 않았음을 해시·파일 목록으로 확인했다.

정답 평균은 각 사례에서 실제로 선택된 구간의 알려진 속도 벡터와 중력으로 계산했다. 이 수치를 기존 축구 영상에 대한 정확도·신뢰구간으로 사용하면 안 된다. 합성 환경은 일정한 프레임 간격, 정확한 공 윤곽, 고정 카메라, 알려진 중력 방향을 사용한다.

실제 32개에는 YOLO·CSRT를 다시 실행하지 않았다. 직전 전체 추론의 저장 관측을 재사용하고 변경한 물리 계산을 실행했다. 입력 영상·가중치·추적 모듈의 해시를 확인했고, 당시 분석 코드 중 이번에 달라진 것은 `shot_physics.py`였다. 시간 경계 수정으로 7개 영상에서 구간 끝의 관측 1개씩(총 7개)이 계산 후보에서 제외됐다. 추적 레코드를 수정한 것은 아니다. 촬영 시간 미확인 29개, 카메라 이동 3개라는 보류 판정은 유지됐다.

## 확인된 한계와 다음 개발

실제 촬영 자료가 없어 다음의 정확도 한계는 남아 있다. 추가 합성 시험에서 광각 영상에 다른 보정을 잘못 선택하고 같다고 확인하면 정답 42.102km/h를 **64.8km/h(약 53.9% 오차)**로 표시할 수 있었다. 공 박스가 매 프레임 일정하게 20% 크면 정답 42.019km/h를 **35.6km/h(약 15.3% 오차)**로 표시할 수 있었다. 두 사례는 정확한 계산의 합격 사례가 아니라 현재 검사가 잡지 못하는 체계적 오차의 재현이다. 작게 나온 투영 오차만으로 실제 속도가 맞다고 결론 내리지 않는다.

실제 촬영 시간·같은 설정의 체커보드·독립 속도 기준이 생기면 현장 오차 검증을 진행한다. 자료를 기다리는 동안에는 **4단계 골대 진입 후보·판정 보류·결과 표시**를 개발할 수 있다. 현재의 초기 물리 모델을 골대까지 외삽하거나 공 중심이 영상의 골대 사각형에 들어왔다는 사실만으로 골인을 확정하지 않는다.
