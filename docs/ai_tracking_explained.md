# AI 2단계 코드를 이해하는 방법

이번 개발의 중심은 **같은 공을 여러 프레임에 걸쳐 연결하고, 그 판단 근거를 남기는 것**이다. 기존 YOLO 모델을 다시 학습한 것이 아니라 검출 결과를 선택·보완·저장하는 코드를 개발했다.

## 어떤 파일이 바뀌었나

| 파일 | 역할 |
|---|---|
| [ball_tracking.py](../backend/ball_tracking.py) — 신규 | 초기 공 선택, Kalman 필터, 같은 공 후보 선택, 슈팅 시작·누락·종료 판단 |
| [goal_geometry.py](../backend/goal_geometry.py) — 신규 | 골대 부품을 하나의 영역으로 조합 |
| [analyze_shot.py](../backend/analyze_shot.py) — 수정 | YOLO·추적·ROI 확대·CSRT 연결, JSON·MP4 저장, 기존 속도 계산기에 관측점 전달 |
| [test_ball_tracking.py](../tests/test_ball_tracking.py) — 신규 | 빠른 슛, 가림, 잘못된 물체 선택, 골대 조합 등의 사례 검사 |
| [run_ai_baseline.py](../tools/run_ai_baseline.py) — 1단계 도구에 추가 | 추적 상태·관측점 수·재탐지 횟수와 새 모듈 해시 기록 |
| [build_ai_gallery.py](../tools/build_ai_gallery.py) — 사진 정리 도구 | 현재 폴더의 영상과 이전 입력 해시를 대조한 뒤 기존 결과 사진을 모음 |

Backend API·Frontend 코드는 이번 2단계에서 변경하지 않았다. 기존 반환 필드를 유지하고 추적 필드를 추가했으므로 Backend의 SSE 결과에 함께 실린다. 새로운 추적 영상 UI는 아직 없다.

## 1. 먼저 슛을 하기 전의 공을 고른다

YOLO가 공이라고 표시한 후보를 모두 받아도 그중에는 로고·신발 같은 오인식이 있을 수 있다. `select_initial_ball()`은 초반 프레임에서 먼저 보이는 후보 중 슈팅 위치에 가까운 공을 고른다. 공이 화면 아래쪽에 있다는 촬영 가정도 사용하므로 모든 촬영 구도에 일반화된 방법은 아니다.

여러 프레임 동안 다른 위치에서 반복 검출되는 물체는 배경 후보로 기록한다. 예를 들어 골대 뒤 로고를 처음부터 슈팅 공으로 고르는 사례를 줄인다.

## 2. 다음 프레임에서 어디로 갈지 예상한다

`PixelKalman`은 공의 화면 좌표 `(x, y)`, 반지름, 각각의 변화 속도를 기억한다. 공이 오른쪽으로 프레임당 약 10픽셀씩 움직였다면 다음에는 오른쪽 10픽셀 근처에 있을 것으로 예상한다.

다음 검출이 오른쪽 12픽셀에 있다면, 예상과 검출을 함께 반영해 위치를 보정한다. 이 과정이 검출 위치와 크기의 흔들림을 줄인다. 이때 기억하는 속도는 **픽셀/초**이며 실제 슈팅 속도 **km/h**는 별도의 물리 계산 결과다.

## 3. 검출된 후보가 같은 공인지 판단한다

`BallTracker._associate()`는 예상 위치와의 거리, 이전 공에 비해 크기가 얼마나 달라졌는지, YOLO 신뢰도를 비교한다. 너무 멀거나 크기 변화가 지나치게 큰 후보는 제외한다.

기존 슈팅 시작 조건은 이동량을 고정된 픽셀 범위로 제한해 빠른 공을 놓치는 사례가 있었다. 새 코드는 공 크기와 영상 해상도를 반영하고, 흐려서 신뢰도가 낮은 공은 연속 관측으로 움직임을 확인한다. 킥 직후 급가속을 허용하되 약한 검출이 비행 방향과 반대인 신발 위치로 튀는 사례는 제외한다.

이 조건은 잘못된 선택을 줄이는 규칙이다. 모든 오인식을 없애거나 여러 개의 공을 동시에 추적하는 기능은 아니다.

## 4. 공을 놓치면 주변을 크게 보고 다시 찾는다

`recover_in_roi()`는 예상 위치 주변만 잘라 YOLO에 다시 넣는다. 전체 영상을 작게 줄여 볼 때 몇 픽셀에 불과하던 공이, 잘라낸 영역을 확대하면 더 크게 보여 검출에 도움이 된다.

잘라낸 영상에서 `(50, 30)`에 공이 있고 자른 영역의 왼쪽 위가 원본 `(800, 400)`이었다면, 원본 좌표는 `(850, 430)`이다. 이 위치를 복원해 모든 좌표를 원본 영상 기준으로 저장한다.

확대 검출도 실패하면 CSRT로 이전 공 모양을 잠깐 따라간다. CSRT 관측은 위치·크기 조건을 통과해야 사용하며, 시작 영역도 영상 경계 안으로 제한한다. CSRT는 YOLO 신뢰도를 제공하지 않고 다른 물체로 이동할 수 있어 출처를 따로 기록한다.

## 5. 관측과 예상 위치를 구분한다

- `yolo`: 모델이 검출한 위치를 관측했다.
- `csrt`: 영상 패턴을 따라간 보조 위치를 관측했다.
- `kalman_prediction`: 실제 관측 없이 움직임으로 예상했다.
- `missing`: 사용할 위치가 없어 좌표를 `null`로 남겼다.

관측 없는 예측은 약 0.2초까지만 저장한다. 약 0.7초 동안 회복하지 못하면 추적을 종료한다. 예측점을 실제 관측점으로 세거나 속도 피팅에 넣지 않는다.

`frame_number`는 0부터 시작하고 `time_sec = frame_number / fps`다. 예를 들어 30FPS 영상의 60번 프레임은 2초다. 기존에 넣던 인위적인 `0.001초` 시간 앵커는 제거했다.

## 6. 골대 부품을 합친다

기존 골대 모델은 골대 전체 대신 왼쪽 기둥·오른쪽 기둥·가로대를 따로 표시하기도 했다. 기둥 하나의 폭을 골대 전체 폭으로 해석하면 이후 거리·속도 계산도 틀어진다.

`assemble_goal()`은 기둥 두 개의 높이, 간격, 위아래 정렬을 비교해 한 골대로 묶고, 가까운 가로대를 함께 반영한다. 전체 골대 형태의 박스가 검출되면 이를 사용할 수도 있다. 기둥 하나만으로는 골대 전체 영역을 만들지 않는다. 이 영역은 사각형 근사값이며 골인 판정은 다음 단계다.

## 결과 사진에서 무엇을 확인해야 하나

`assets/ai_stage2/`에 로컬로 보관한 실촬영 20개와 테스트 12개의 결과 JPG에서 선은 당시 물리 모델의 궤적과 미래 예측이다. 실제 공 관측을 그대로 이은 선이 아니다. 일부 선이 지면으로 꺾이거나 속도가 150km/h에 몰리는 문제는 다음 3단계의 카메라·물리 계산 수정 대상이다. 커브 문구도 당시 피팅 계수로 만든 표시다.

실제 추적을 확인하려면 추적 MP4의 공 박스·중심과 원본 공 위치를 비교하고 JSON의 `source`를 확인해야 한다. 추적 MP4의 청록색 사각형은 골대, 노란 원은 필터 위치·반지름, 초록 박스는 YOLO 관측이다. 경로는 관측 시 초록색, 예측 시 자홍색으로 표시된다.

2단계 전체 실행은 34개 중 33개가 속도·이미지를 반환했다. 이후 폴더에서 `test_videos/video5.mp4`, `test_videos/video6.mp4`가 없어져 현재는 32개다. 남은 입력 해시를 기존 실행과 대조했고 해당 결과 32개 모두 반환 성공이었다. 새로 재실행하거나 정확도를 측정한 결과는 아니다.

정확한 검증 수치와 남은 범위는 [2단계 결과 문서](ai_stage2_results.md)에 기록했다. 다음 개발은 카메라 보정과 비행 구간의 3D 좌표·속도 계산이다.
