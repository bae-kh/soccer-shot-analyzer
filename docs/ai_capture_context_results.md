# 촬영 시간·카메라 설정 연동

2026-10-11. 공 오검출 및 공 크기·비행 구간 개선에 이어 실제 시간 기준과 카메라·줌별 보정을 연결했다. 실제 촬영값 또는 속도 정답을 새로 확보한 것은 아니다. README는 이번 작업에서 수정하지 않는다.

## 바뀐 동작

- 촬영 시간을 `unknown`, `normal`, `slow_motion`으로 구분한다. 정상 속도 원본·일정 FPS를 사용자가 확인한 경우만 파일 FPS를 실제 시간으로 사용한다.
- 일정한 슬로모션 배율을 알면 `실제 시간 = 파일 재생 시간 / 배율`로 변환한다. 실제 촬영 FPS를 사용할 때는 촬영 프레임이 중복·삭제·보간 없이 한 장씩 저장됐다는 확인도 필요하다. FPS 숫자만으로 슬로모션 배율을 추측하지 않는다.
- 시간 환산 후 **비행 구간의 길이·관측 간격·중력 모델을 다시 계산**한다. 계산된 속도에 배율만 곱하지 않는다. 프레임별 추적 JSON의 `time_sec`와 디버그 영상 FPS는 재생 시간을 유지하고, 3D 결과의 `time_sec`는 실제 시간을 사용한다. `video_metadata.tracking_time_basis`와 `flight_segment.time_basis`로 구분한다.
- 카메라·렌즈·줌·촬영 모드별 보정을 별도 JSON으로 저장한다. 다른 보정을 덮어쓰거나 기존 전역 `calibration.json`을 모든 영상에 자동 적용하지 않는다. 기존 파일은 보존된다.
- 같은 설정 및 크롭하지 않은 영상이라는 확인이 있어야 보정을 적용한다. 해상도 크기만 같은 비율로 바뀌면 초점거리·중심좌표를 함께 환산한다. 화면 비율이 0.5% 넘게 다르면 보류한다. 같은 비율의 크롭은 자동 감지할 수 없으므로 사용자 확인도 필요하다.
- 시간이 미확인 또는 카메라 보정이 누락됐으면 `speed: null`, `measurement_status: UNAVAILABLE`로 반환한다. 모든 보류 사유는 `measurement_context.problems`에 저장하고 화면에도 표시한다. 공 궤적·관측 이미지·추적 영상은 계속 생성한다.

추적기의 픽셀 움직임·복구 정책은 이번 작업에서 바꾸지 않았다. 슬로모션에서 필요한 실제 비행 길이만큼 공을 추적하지 못하거나 중복 프레임이 포함되면 조건 입력 후에도 관측 부족으로 보류할 수 있다. 편집 구간마다 배율이 달라지는 영상, 가변 FPS의 프레임별 타임스탬프, 자동 렌즈·크롭 전환은 아직 지원하지 않는다. 그런 영상은 미확인으로 둔다.

## 화면·API 사용법

1. 카메라 버튼에서 슈팅과 같은 설정의 체커보드 영상을 업로드한다. 내부 교차점 9×6개(칸 10×7)를 여러 각도에서 촬영한다. 설정 이름을 입력하면 별도 보정 프로필이 저장된다.
2. 슈팅 영상 선택 전에 정상 속도 원본인지 확인하거나 일정한 슬로모션 배율을 입력한다. 실제 촬영 FPS만 알고 있으면 프레임 저장 방식도 확인한다.
3. 해당 보정을 선택하고 같은 카메라·렌즈·줌·촬영 모드, 크롭 없는 영상인지 확인한 뒤 영상을 선택한다. 모르는 조건은 미확인으로 둬도 궤적 분석은 실행할 수 있다.

`POST /analyze`는 multipart `file`과 JSON 문자열 `capture_options`를 받는다. 사용할 수 있는 필드는 다음과 같다.

| 필드 | 의미 |
|---|---|
| `timing_mode` | `unknown`, `normal`, `slow_motion`; 기본값 미확인 |
| `slowdown_factor` | 실제 1초가 재생 몇 초인지, 1 이상의 일정 배율 |
| `capture_fps` | 실제 촬영 FPS; 배율과 함께 입력하면 일치 여부 검사 |
| `one_frame_per_capture` | 촬영 FPS 사용 시 프레임 중복·삭제·보간 없음 확인 |
| `intrinsics_profile_id` | `/camera-profiles`에서 조회한 보정 ID |
| `same_camera_settings` | 카메라·렌즈·줌·촬영 모드 일치 확인 |
| `uncropped` | 크롭 없이 원본 또는 같은 비율로 리사이즈한 영상임을 확인 |

잘못된 값·임의 보정 파일 경로는 422로 거절한다. 업로드는 고유 ID로 저장해 동명 영상이 덮어쓰지 않도록 했다. `POST /calibrate`는 multipart `profile_label`을 받아 완료 결과에 `profile_id`를 반환한다. `GET /camera-profiles`는 유효한 보정만 반환한다. 보정 JSON은 로컬 `backend/camera_profiles/<ID>.json`에 저장하며 Git에서는 제외한다.

예시 영상은 `docs/video_capture_conditions.json`의 `reports`에서 조건을 읽는다. 확인한 값만 `video_options`에 해당 영상의 상대 경로를 키로 추가한다. 예를 들어 정상 속도 원본임을 확인한 영상에 `timing_mode: normal`을 지정하고 실제 보정 ID와 확인 항목을 넣는다. 슬로모션 1~4, 줌아웃 10~13 등의 값은 현재 **null/미확인**으로 유지한다. 업로드된 `video1.mp4`를 예시 `test_videos/video1.mp4`로 자동 취급하지 않는다.

## 검증

| 검증 | 결과 |
|---|---|
| Python 전체 테스트 | 66개 통과 |
| 프런트엔드 | 빌드·린트 통과, SSE 테스트 4개 통과 |
| 32개 원본 영상의 YOLO·CSRT 전체 재실행 | 32개 모두 추적 JSON·결과 이미지·관측 이미지·추적 영상 생성 |
| 직전 단계와 프레임별 추적 전체 비교 | 32/32 영상의 모든 추적 레코드·궤적 동일; 영상·모델 해시 동일 |
| 촬영 조건 경로 연결 | 슬로모션 4개, 줌아웃 4개, 설정 변화 의심 3개, 미확인 21개 |
| 실제 속도 표시 | 32개 모두 보류. 대표 사유 촬영 시간 미확인 29개, 카메라 이동 3개. 모든 영상에 시간 미확인·보정 누락도 기록 |
| 원본 좌표·프레임·미디어·코드 해시 검사 | PASS |
| 실제 화면 | 배율/FPS 입력 전환, 프레임 저장 확인, 보정 모달·이름 입력, test1 업로드 → 궤적 이미지 및 두 보류 사유 확인 |

기존 단계의 15개 `ESTIMATED`는 파일 FPS·기본 화각 등 가정을 사용한 조건부 추정이었다. 이번에는 실제 촬영 조건이 확인되기 전 숫자를 보여주지 않도록 정책을 바꿨다. **32개 보류가 새 공 추적 실패 32개를 뜻하지 않는다.** YOLO 1,790점, CSRT 694점, 예측 67점, 누락 354점은 직전과 동일하다. 실행 시간 평균 14.682초는 프로세스 시작·모델 로드를 포함하며 속도 최적화 수치로 해석하지 않는다.

시간 환산 테스트에서는 실제 120FPS로 만든 알려진 합성 궤적을 재생 30FPS로 표현했다. 4배 배율을 적용한 결과가 실제 120FPS 기준 계산과 같은 비행 프레임·속도를 반환하고, 재생 0.45초보다 긴 프레임 구간을 실제 시간으로 선택하는지 확인했다. 원본 추적의 재생 시간은 유지됐다. FPS와 배율의 모순, 숫자만 있는 촬영 FPS, 잘못된 보정 경로, 다른 화면 비율, 미확인 설정도 검사했다.

카메라 보정 저장 API 검증은 계산부를 모의 처리하여 별도 ID 두 개·보정 이름·목록 조회가 맞는지 검사한 것이다. 원본 촬영 장비의 실제 체커보드로 검증한 결과가 아니다. 독립 실측 속도 정확도와 해당 촬영 장비의 보정 정확도는 아직 검증 대상 값이 없다.

## 다음에 필요한 값

1. 슬로모션 test1~4의 일정한 재생 배율 또는 실제 촬영 FPS와 프레임 저장 방식. 가능하면 정상 속도 원본으로 확인한다.
2. 카메라·렌즈·줌·촬영 모드별 실제 체커보드 보정과 해당 영상에 사용할 프로필 확인. 줌아웃/광각 그룹에 다른 보정을 연결한다.
3. 새로 고정 카메라로 촬영한 공 궤적과 독립 속도 기준으로 오차를 평가한다. 설정을 입력했다고 속도 정확도가 검증된 것은 아니며, 공 박스의 실제 크기·가림·중력 방향 등 기존 불확실성은 남아 있다.
